# 5s-helpdesk

База знаний техподдержки 5SYSTEMS: статьи формата «проблема и решение».

Контекст продукта: [5systems.ru/articles](https://www.5systems.ru/articles)

## Структура

Материалы разложены по трем корневым разделам:

```
articles/                    # статьи базы знаний, по продуктам
├── 5S AUTO/                 # разделы повторяют 5systems.ru/articles
│   ├── Полезное/
│   ├── CRM/
│   ├── ...
│   └── Внешние обработки/    # своего раздела на сайте нет
├── 5S LINK/
├── 5S Chat/
├── 5S Cloud/
├── 5S TSD/
├── 5S Pay/
├── 5S Remzona/
└── 5S AI Agent/

tips/                        # советы формата «проблема и решение»
├── 5S AUTO/
├── Оборудование/
│   ├── Банковские терминалы/
│   └── Кассы ККМ/
└── Техподдержка/

lessons/                     # уроки
```

Каждая статья — отдельная папка с уникальным именем:

```
.../тема-статьи/
├── tema-stati.md
└── attachments/             # скриншоты и файлы статьи
```

## Время чтения и дата обновления

Сразу под заголовком идет служебный блок — таблица в одну строку. В статьях в ней две колонки, в советах одна: время чтения там не показываем.

```markdown
# Канбан сделок

<table><tr><td><b>Время чтения:</b> 11 мин.</td><td><b>Обновлено:</b> 25.08.2026</td></tr></table>
```

```markdown
# Касса не включается

<table><tr><td><b>Обновлено:</b> 24.08.2026</td></tr></table>
```

Скрипт понимает три вида блока — таблицу, две строки и одну (`*11 мин. · Обновлено 25.08.2026*`) — и сохраняет тот, что уже стоит в файле. Так что переключить оформление можно разом, не правя статьи руками.

Границы таблицы на GitHub видны: он рисует их своим CSS, а атрибут `style` вырезает санитайзер. На сайте оформление задается вашими стилями.

**Время чтения** — редакторская оценка, ее ставит автор. Строка есть только у статей в `articles/`: советы короткие, минуты для них ничего не говорят. Скрипт подставляет значение один раз, при появлении статьи, и больше эту строку не трогает. Как считаем:

- **новая статья** — расчетное значение: объем текста при 150 словах в минуту плюс по 10 секунд на скриншот, с округлением вверх;
- **перенос со старой базы знаний** — среднее между расчетным и тем, что указано на `5systems.ru/help`, с округлением вверх. Цифры на сайте выставлялись вручную и обычно выше расчетных, а обещать читателю меньше, чем он привык, не стоит.

**Дата** ведется автоматически: `.scripts/update-meta.py` ставит текущую, если изменился текст материала. Правка одних служебных строк, переименование папки и переоформление шапки датой не считаются, иначе она поднималась бы на пустом месте. Руками эту строку править не нужно.

Подпись у даты зависит от того, правили ли материал после появления:

- **Создано** — с момента создания текст не меняли;
- **Обновлено** — вносили изменения, дата относится к последней правке.

У статей, перенесенных со старой базы знаний, подпись всегда «Обновлено»: там их уже правили, и «Созданной» такая статья не бывает. Дата берется **с сайта** (она видна рядом с заголовком статьи) и держится, пока мы текст не тронули; после нашей правки встает наша. Скрипт узнает такие статьи по строке источника со ссылкой на `5systems.ru/help`.

Учтите: `--from-git` пересчитывает даты по истории репозитория и проставленные с сайта даты затрет.

Обе строки попадают в `index.json` (`reading_time` и `updated_at`), оттуда их берет сайт. Дата в индексе — та же, что в статье: источник один.

Ниже служебных строк идет источник — откуда статья перенесена:

```markdown
<sub>Источник: https://www.5systems.ru/help/kanban-sdelok</sub>
```

Строка временная: после переезда на новую базу знаний ее уберут отовсюду, поэтому она набрана мелким шрифтом и не мозолит глаза.

Пересобрать вручную:

```bash
python3 .scripts/update-meta.py
```

Массовая косметическая правка (переоформили строку сразу во всех статьях, поправили общую опечатку) — не повод поднимать дату обновления везде. В таком случае:

```bash
KEEP_DATES=1 git commit -m "..."
```

Проставить даты заново по истории git — `python3 .scripts/update-meta.py --from-git`.

## Индекс материалов

`index.json` в корне — список материалов (для автоматического анализа изменений). У каждого две даты: `updated_at` — та, что показана в самой статье, и `added_at` — когда материал появился в репозитории. Порядок в списке — по `added_at`, от свежих к старым: дата в статье может быть сайтовой и уводила бы только что перенесенный материал в конец. Переименование папки датой появления не считается.

Там же, в `sections`, — дерево разделов в нужном порядке. Порядок смысловой, а не алфавитный (для 5S AUTO он повторяет порядок на сайте), поэтому задается вручную: файл `.order` кладется в саму папку раздела и перечисляет вложенные разделы — по одному в строке. См. [articles/.order](articles/.order) и [articles/5S AUTO/.order](articles/5S%20AUTO/.order). Разделы, не указанные в `.order`, дописываются в конец по алфавиту.

Тем же файлом задается и порядок самих статей внутри раздела — просто перечислите папки статей: см. [articles/5S AUTO/CRM/.order](articles/5S%20AUTO/CRM/.order). Позиция попадает в `index.json` полем `order`; у неперечисленных материалов оно больше, чем у любого из списка, так что они оказываются в конце.

GitHub показывает дерево файлов только по алфавиту — на его боковую панель `.order` не влияет.

Пересобрать вручную:

```bash
python3 .scripts/generate-index.py
```

Чтобы индекс обновлялся при коммите, один раз включите hooks репозитория:

```bash
git config core.hooksPath .githooks
```
